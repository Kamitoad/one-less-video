# OneLessVideo architecture

## System shape

OneLessVideo is a Manifest V3 extension generated by WXT. It has three entrypoints and no background service worker:

1. the YouTube content script composes navigation, player, controller, overlay, and settings modules;
2. the popup changes the global enabled setting and opens options;
3. the options page validates and stores friction settings.

The domain code is ordinary TypeScript. WXT is build and lifecycle infrastructure rather than an application framework.

## Extension lifecycle

The content script starts at `document_start` for `https://www.youtube.com/*`, loads normalized settings from `browser.storage.local`, then creates one `InterventionController`. A storage-change subscription updates the controller in open tabs. Page unload and WXT context invalidation dispose the controller, navigation watcher, player lock, overlay, timers, and extension listeners.

Disabling settings is synchronous from the controller's perspective: it aborts the current run and releases the player. Re-enabling on a current watch page starts one new run. Other settings changes are used by the next intervention so a partly completed interaction does not change underneath the user.

## YouTube SPA detection

`youtube-navigation.ts` treats YouTube as an unstable external platform. It checks the URL initially and reacts to:

- WXT's `wxt:locationchange` window event;
- YouTube's `yt-navigate-finish` document event;
- `popstate`;
- a 500 ms URL polling fallback.

The watcher emits only when the complete URL changes. The controller separately deduplicates by parsed `videoId`, so query/hash noise and repeated platform events cannot create parallel interventions. No page-world script and no `history.pushState` patch are required.

`getYouTubeVideoId` is a pure function. Version 1 accepts only normal `/watch?v=...` URLs on the supported YouTube host; Shorts are deliberately excluded.

## Player locking

`youtube-player.ts` is the only module containing player selectors. A run creates a short-lived lock that:

- finds and pauses the current video element;
- listens for `play` and pauses again while locked;
- watches DOM replacement with `MutationObserver` plus a bounded-frequency lookup fallback;
- moves the listener when YouTube swaps the video node;
- removes the listener, observer, DOM-ready hook, timer, and abort hook on release.

Approval captures the current video, releases every lock resource first, and then calls `play()`. A rejected play promise is reported locally but does not restore the lock. This is the intentional fail-open behavior.

## Intervention lifecycle and race strategy

The state is a discriminated union: idle, locking, asking intent, countdown, challenge, decision, approved, or aborted. Every non-idle state is associated with one `videoId`.

Each run owns both a monotonic `runId` and an `AbortController`. Starting video B increments the ID, aborts A, releases A's player session, and mounts B. Every stage callback and final outcome verifies both the run ID and video ID before changing state or approving playback. Therefore a late countdown, challenge, promise, or click from A cannot affect B even if an adapter fails to honor cancellation.

Unexpected internal errors release the player and remove the overlay. OneLessVideo is productivity tooling, not a security boundary, so the system fails open.

## Intervention plan and UI

`buildInterventionPlan` converts validated settings and an injected `RandomSource` into immutable per-run choices: countdown duration, challenge value, and final-button position. Random values are selected once per intervention and are deterministic in tests.

The overlay is mounted in an open Shadow DOM to isolate OneLessVideo and YouTube styles. It uses semantic forms, labels, radio buttons, live validation messages, visible focus states, a focus boundary, and no animation. The final action chooses from a fixed responsive position set and never moves after rendering. The host is scrollable at small viewport heights.

The reason and intention exist only in the mounted DOM. They are neither returned to the controller nor persisted or logged.

## Settings and storage

Only the versioned envelope `{ schemaVersion: 1, settings }` is stored under one `browser.storage.local` key. Unknown envelopes return defaults. Known envelopes are normalized field by field with central numeric bounds, and the options page reports invalid ranges before saving. This keeps a future v1-to-v2 migration point without adding a migration framework prematurely.

The manifest requests only `storage`. Content-script host access is limited to `https://www.youtube.com/*`.

## Test strategy

- Pure Vitest tests cover URL identity, settings normalization/versioning, random plans, challenge generation, and abortable countdowns.
- Controller tests use deliberately non-cooperative promises to prove stale A cannot approve B, deduplication, abort, disable/re-enable, and fail-open cleanup.
- JSDOM tests cover player event cleanup and replacement plus the complete overlay validation sequence.
- Playwright loads the production MV3 build into a persistent Chromium context. YouTube navigation is intercepted with a controlled HTML fixture, avoiding live-site flakiness while retaining the real content-script match and storage behavior.
- A manual live-YouTube checklist remains necessary because the external DOM can change independently of the repository.
